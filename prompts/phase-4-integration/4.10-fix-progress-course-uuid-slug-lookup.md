# Phase 4.10: Fix Progress Course UUID vs Slug Lookup & Validation

## Goal
Resolve PostgreSQL `QueryFailedError: invalid input syntax for type uuid: "python-for-data-work"` on `GET /api/progress` and `GET /api/progress/completed-ids`, and prevent 400 Bad Request on `POST /api/progress` and `PATCH /api/progress/complete` when clients pass course slugs or UUIDs. Ensure seamless bidirectional support for course UUIDs and slugs across backend progress endpoints and frontend consumers.

## Decisions & Assumptions
1. **Defensive Dual Support (Backend)**: Backend must accept both course UUID and course slug.
   - If a valid UUID string is passed (`/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`), use it directly.
   - If a slug string is passed (not UUID), resolve it to `course.id` using `CoursesRepository.findBySlug(slug)`.
   - If querying progress for an unknown slug, return `[]` gracefully without database casting errors.
   - If attempting to upsert/toggle progress with an unknown slug, throw `NotFoundException("Course '<slug>' not found")`.
2. **DTO Validation**: Change `@IsUUID()` on `courseId` in `UpsertProgressDto` and `ToggleCompleteDto` to `@IsString() @IsNotEmpty()`, allowing both UUIDs and human-readable slugs while maintaining payload validation.
3. **Frontend Precision**: In `CourseDetailPage` and `LearningPage`, pass `String(course.id || course.slug)`. When `course.id` (UUID) is loaded, it is passed directly, eliminating extra slug lookups.
